# Auth throttling behind Railway ingress

Fastify is constructed without `trustProxy`. The TCP peer seen by the API is the shared Railway ingress proxy, not necessarily the end user. `request.ip` is therefore unsuitable as a low-volume auth key: 100 attempts on that peer can lock out unrelated accounts. Do not replace it with raw `X-Forwarded-For` or other client-supplied headers; they can be forged. A verified client-IP key requires a separately reviewed proxy trust boundary (known proxy hops/ranges and confirmed header rewriting at the edge).

`/api/auth/register`, `/login`, `/password/request`, and `/password/confirm` use atomic Postgres counters, shared by all API instances. The identity keys are SHA-256 hashes of endpoint, scope, and normalized email (or reset-token hash for confirm). Per-identity caps remain 3 registrations/hour, 5 logins/15 minutes, 5 reset requests/hour, and 5 confirms/15 minutes. These prevent repeated guessing for a single account or token across instances or source addresses. A separate endpoint-wide shared cap of 10,000 attempts/hour prevents unbounded abuse with rotating identities, but can still affect everyone at very high volume; it is a backstop rather than a per-client policy. Normal traffic from different accounts no longer shares the 100-attempt budget. The Fastify instance-local general limit is 10,000 requests/minute (emergency backstop), also keyed on socket IP; neither cap is a substitute for verified edge-level protection. Limits emit 429 with `Retry-After` in seconds and reset after their window. No proxy forwarding header is used by these keys.

The global counter is claimed before any per-identity counter. Once it is exhausted, further rotating emails/tokens cannot create identity rows; saturated counters stop at cap + 1. This does not prevent a single actor from consuming the global budget and denying auth to legitimate users. Global-first also charges the global budget for per-identity rejections. Neither a larger cap nor client-provided forwarding headers solve that availability issue.

Operational follow-up (security release gate): verify the Railway ingress topology and deploy a trusted edge-level per-client throttle before treating this as public-release-ready. Monitor 429 rates and Postgres counter growth; size the global cap from measured traffic, not guesses. The recovery email path is currently a stub; this change does not enable email delivery. Changing proxy trust, edge headers, or production limits needs an explicit security review and verified topology.
